## 1. Resumo executivo

O Gymbro é um sistema de registro de treino. O valor do produto é registrar carga, reps e volume sem
atrito e devolver a próxima decisão de progressão. A interface deve parecer um caderno técnico de
treino, não um feed de cards motivacionais.

O aplicativo mobile Expo foi apagado. O frontend atual é um PWA mobile-first em `web/`, com:

- Next.js 16.4.6 (App Router)
- React 19.3.0
- TypeScript strict
- pnpm
- Zod 4
- Jotai 3
- Axios
- Lucide React
- CSS Modules com tokens do brand guide

O backend continua em `backend/`, Spring Boot 4.1.1 com Java 21. O serviço Python de parsing de
bioimpedância fica em `doc-process/`.

Já existem as duas primeiras telas: `/signin` e `/signup`, integradas à API. O cadastro cria a conta
e já abre a sessão. A autenticação usa cookies `HttpOnly`, não tokens no corpo da resposta nem tokens
no `localStorage`.

Ainda não existe a casca autenticada do app (as quatro abas) nem o guard de rotas privadas. Hoje,
após login/cadastro, o usuário vai para `/`, que ainda é a página placeholder criada pelo scaffold do
Next (“Hello world!”).

### 4.4 Formulários

Fluxo de login (`SignInForm`):

1. Valida `loginSchema` no cliente.
2. `POST /api/auth/login` com e-mail e senha.
3. O backend responde `200` com `UserDto` e define os cookies.
4. O front guarda `{ user }` no Jotai.
5. Redireciona para `safeNextPath(next)` ou `/`.

Fluxo de cadastro (`SignUpForm`):

1. Valida `signUpSchema` no cliente.
2. `POST /api/auth/register`.
3. O backend cria a conta, abre a sessão e responde `201` com `UserDto` + cookies.
4. O front guarda `{ user }` no Jotai.
5. Redireciona para `safeNextPath(next)` ou `/`.

O cadastro não faz mais uma segunda chamada de login. O backend faz a criação da conta e a emissão da
sessão na mesma transação.

Links entre telas:

- Signin: “Ainda não possui conta?” + “Criar conta”.
- Signup: “Já possui conta?” + “Entrar”.
- O `?next=` é preservado ao alternar entre as telas.

Estados implementados:

- label persistente em todos os campos;
- erros junto ao campo com `aria-invalid` e `aria-describedby`;
- botão desabilitado e `aria-busy` durante envio;
- loading com três barras pulsando, não spinner circular;
- foco visível;
- password reveal com `aria-label` e `aria-pressed`;
- `safeNextPath` rejeita `//`, `\` e destinos que não começam com `/`;
- erros da API traduzidos para PT-BR.

## 5. Autenticação e sessão

Esta é a parte mais importante para o próximo agente não regredir.

### 5.1 Decisão final

A sessão do PWA usa cookies `HttpOnly` definidos pelo backend.

O PWA:

- nunca recebe tokens no corpo da resposta;
- nunca lê tokens via JavaScript;
- nunca persiste tokens em `localStorage` ou `sessionStorage`;
- guarda apenas os dados públicos do usuário no Jotai/localStorage;
- envia cookies automaticamente via `withCredentials: true`.

### 5.2 Cookies

Implementados em `backend/src/main/java/com/gbatistadev/gymbro/auth/AuthCookies.java`.

| Cookie | Path | Duração | Atributos |
| --- | --- | --- | --- |
| `gymbro_access` | `/api` | 15 min (`JWT_EXPIRATION_MS`) | `HttpOnly`, `SameSite=Strict`, `Secure` configurável |
| `gymbro_refresh` | `/api/auth` | 180 dias (`JWT_REFRESH_EXPIRATION_MS`) | `HttpOnly`, `SameSite=Strict`, `Secure` configurável |

Configuração em `backend/src/main/resources/application.yaml`:

```yaml
app:
  auth:
    cookie:
      secure: ${AUTH_COOKIE_SECURE:false}
      same-site: ${AUTH_COOKIE_SAME_SITE:Strict}
      domain: ${AUTH_COOKIE_DOMAIN:}
```

Produção:

- `AUTH_COOKIE_SECURE=true` obrigatório em HTTPS.
- `SameSite=Strict` assume PWA e API no mesmo site.
- Se PWA e API estiverem em sites distintos, será necessário `SameSite=None` + `Secure=true` e
  proteção CSRF adicional.
- `AUTH_COOKIE_DOMAIN` é opcional; vazio = host-only.

### 5.3 Endpoints de autenticação

`POST /api/auth/register`

- Público.
- Cria o usuário e já emite access + refresh cookies.
- Retorna `201` com `UserDto` (sem tokens).
- `Cache-Control: no-store`.

`POST /api/auth/login`

- Público.
- Valida credenciais e emite access + refresh cookies.
- Retorna `200` com `UserDto` (sem tokens).
- `Cache-Control: no-store`.
- Mantém o rate limit existente: 5 tentativas por IP + e-mail em 15 minutos.

`POST /api/auth/refresh`

- Lê `gymbro_refresh` do cookie.
- Emite um novo `gymbro_access`.
- Retorna `204` sem corpo.
- `Cache-Control: no-store`.

`POST /api/auth/logout`

- Lê `gymbro_refresh` (e opcionalmente o access cookie).
- Revoga a sessão no banco.
- Limpa os dois cookies com `Max-Age=0`.
- Retorna `204`.

### 5.4 Backend

Arquivos principais:

```text
backend/src/main/java/com/gbatistadev/gymbro/auth/
  AuthController.java
  AuthService.java
  AuthCookies.java
  AuthSession.java
  LoginRateLimiter.java
  dto/LoginDto.java
```

`AuthService`:

- `register(CreateUserDto)` é `@Transactional`, cria o usuário e chama `issueSession`.
- `login(LoginDto)` valida a senha e chama `issueSession`.
- `refresh(String rawRefreshToken)` valida o hash no banco e emite novo access token.
- `logout(String rawRefreshToken, UUID userId)` revoga por hash ou todas as sessões do usuário.
- `issueSession` gera o refresh token, salva o hash e gera o access JWT.

`AuthController`:

- Monta os cookies via `AuthCookies`.
- Usa `@CookieValue(name = AuthCookies.REFRESH, required = false)`.
- Nunca devolve `AuthTokensDto`; esse DTO foi removido.
- `RefreshRequest` também foi removido.

`JwtAuthenticationFilter`:

- Lê primeiro o cookie `gymbro_access`.
- Mantém `Authorization: Bearer` como fallback para clientes não-browser.
- O PWA não usa Bearer.

`SecurityConfig`:

- `SessionCreationPolicy.STATELESS`.
- CSRF desabilitado com a justificativa de cookies `SameSite=Strict`.
- APIs privadas retornam `401` no contrato de erro padrão.

`CorsConfig`:

- `allowCredentials(true)`.
- Origem padrão apenas `http://localhost:3000`.
- Origens explícitas via `CORS_ALLOWED_ORIGINS`.
- Nunca usar `*` com credenciais.

`OpenApiConfig`:

- Declara `cookieAuth` (`apiKey` no cookie `gymbro_access`) e `bearerAuth` para clientes não-browser.
- O snapshot é gerado por `OpenApiContractIT` em `docs/api/openapi.json`.

### 5.5 Frontend: refresh e 401

`web/src/lib/http.ts`:

- Cria Axios com `baseURL` de `env.NEXT_PUBLIC_API_URL` e `withCredentials: true`.
- Em `401`, ignora login/register/refresh e tenta refresh uma única vez.
- O refresh é single-flight: várias requisições 401 compartilham a mesma promessa.
- Se o refresh funcionar, repete a requisição original.
- Se falhar, remove a sessão, limpa o `localStorage` e chama o handler de navegação.
- O handler é registrado em `AppProviders` com `useRouter` e `useSetAtom`.
- O handler precisa estar dentro do `<Provider>` do Jotai para limpar o store correto.

`web/src/stores/session.ts`:

```ts
export const SESSION_STORAGE_KEY = "gymbro.session";

export type Session = {
  user: UserSummary;
};

export const sessionAtom = atomWithStorage<Session | null>(
  SESSION_STORAGE_KEY,
  null,
);
```

Não existe mais `tokens` no tipo `Session`. Não reintroduzir.

### 5.6 Limites conhecidos da sessão

- O access token continua válido até expirar depois do logout, porque o JWT é stateless.
- Não há rotação de refresh token.
- Não há denylist de JWT (`jti`).
- O refresh token é revogado no banco no logout.
- O login rate limit existe apenas no login, não no cadastro.
- O cadastro abre sessão na mesma transação; se a emissão do refresh falhar, a criação do usuário
  também sofre rollback.

## 6. Contratos e tratamento de erros

### 6.1 Contrato de erro

Definido em `docs/adr/0001-contrato-de-erro.md`:

```json
{
  "timestamp": "2026-11-10T10:00:00",
  "status": 409,
  "code": "SESSION_ALREADY_ACTIVE",
  "message": "An open session already exists",
  "path": "/api/sessions",
  "errors": []
}
```

O cliente testa `code`, não `message`.

`web/src/contracts/api-error.ts` valida esse shape com Zod.

`web/src/features/auth/errors.ts`:

- Mapeia erros de validação do Zod para campos.
- Traduz códigos como `UNAUTHENTICATED`, `TOO_MANY_ATTEMPTS` e
  `RESOURCE_ALREADY_EXISTS`.
- Mostra mensagem geral quando não há erro de campo.
- Usa mensagens de campo em PT-BR.

- `userSummarySchema`
- `loginSchema`
- `signUpSchema`

`AuthTokensDto` e `RefreshRequest` foram removidos do backend e não existem mais no frontend.

## 10. Riscos e pontos de atenção

- **Não reintroduzir tokens no `localStorage`.** O único dado persistido no PWA é o usuário público.
- **Não voltar a devolver tokens no corpo da resposta.** O backend atual não faz isso.
- **`SameSite=Strict` exige PWA e API no mesmo site.** Para domínios distintos, configurar
  `SameSite=None`, `Secure=true` e CSRF token.
- **`Secure=false` é só para desenvolvimento HTTP local.** Em produção, usar
  `AUTH_COOKIE_SECURE=true`.
- **CORS com credenciais não aceita `*`.** Manter origens explícitas.
- **O access token não é revogado no logout.** Isso é uma limitação conhecida do JWT stateless.
- **Sessões antigas do navegador** podem ter o formato antigo `{ tokens, user }` no
  `localStorage`. O próximo login sobrescreve. O recomendado é o usuário sair e entrar novamente.
- **Bearer continua aceito no backend** como fallback para clientes não-browser. O PWA não envia
  `Authorization`. Se o objetivo for remover totalmente, será preciso atualizar testes de integração
  que geram JWT interno.
- **Não há Tailwind nem shadcn instalados.** A interface usa CSS Modules e os tokens do brand guide.
  Se o próximo agente quiser adotar Tailwind/shadcn, isso deve ser uma decisão explícita, não um
  efeito colateral.
- **A página `/` ainda é placeholder.**
- **Não há service worker/PWA instalável ainda.**
- **O build do Next usa `next/font/google`**, então a primeira build precisa de rede para baixar as
  fontes IBM Plex. Elas são servidas localmente pela build depois.

6. As telas `/signin` e `/signup` foram implementadas com layout compartilhado, tokens do brand guide,

7. O usuário apontou que o cadastro não fazia login automático. Primeiro o front passou a chamar login
   após register; depois, na migração para cookies, o backend passou a criar a sessão no próprio
   register.
8. O usuário pediu para substituir o modelo Bearer/localStorage por cookies `HttpOnly`.
9. O backend foi migrado para cookies de sessão, CORS com credenciais, refresh por cookie, logout com
   limpeza de cookies e testes atualizados.
10. O frontend foi migrado para `withCredentials`, refresh single-flight em 401, sessão Jotai apenas
    com dados públicos e remoção de qualquer token do estado/localStorage.
11. Esta documentação de handoff foi criada para continuidade em outra máquina.
