## 3. Tasks 1–5: o que foi feito e as decisões que divergiram do plano

### Task 1 — Migration `users.username` (commit `abcfee4` + `3825f20`)

- A coluna nasce anulável, backfill em PL/pgSQL (parte local do e-mail → minúsculas → sanitiza →
  sufixo numérico em colisão → fallback `user_<hex>` quando inválido), depois `NOT NULL`, índice
  único `lower(username)` e `CHECK` de formato.
- `UsernameMigrationIT` migra até V11, insere 8 contas "legadas" e sobe para V12 — único jeito de
  exercitar o backfill.
- **Divergência:** o plano previa `DEFAULT` temporário para inserts antigos; foi adicionado e depois
  **removido na Task 2** (banco local estava em V11, nada tinha aplicado a V12). Não existe mais
  `DEFAULT` em `users.username`.
- **Lição do teste:** o `DEFAULT` preenchia as linhas antes do backfill, e o `CHECK` barrava
  maiúsculas antes do índice único — ambos pegos pelo IT antes do merge.

### Task 2 — username no domínio e cadastro (commits `a9e660d`, `1a240d6`)

- `User.username` (`NOT NULL`, 30), `CreateUserDto.username` (`@NotBlank`, `@Size(3–30)`, `@Pattern`),
  `UserDto` + `UserSummaryProjection` expostos, service normaliza para minúsculas.
- `ResourceAlreadyExistsException` ganhou `field` opcional; 409 de username devolve
  `errors:[{field:"username"}]` para a Task 15 mostrar o erro embaixo do input.
- **Divergência:** `@Pattern` aceita maiúsculas e o service normaliza — pattern restrito +
  normalização seriam contraditórios. O `CHECK` do banco continua garantindo o formato final.

### Task 3 — login por e-mail ou username (commit `5f1ed99`)

- `LoginDto` virou `{identifier, password}` (`@Size(max 254)`, sem `@Email` — validar formato aqui
  quebraria username).
- `UserRepository.findByIdentifier`: `lower(email) = lower(:identifier) OR lower(username) = ...`.
- Rate limit usa identificador em **minúsculas** (sem isso, alternar a caixa multiplicava as
  tentativas).
- **Armadilha encontrada:** script de migração dos testes trocou `findByEmail` → `findByIdentifier`
  também no caminho de `register` (que usa `CreateUserDto.email`); quebrou `shouldRegisterUser` com
  500. Corrigido de volta para `findByEmail` naquele stub.

### Task 4 — `PUT /api/users/me/password` (commit `4d8bd4a`)

- 204 no sucesso; senha atual errada → **400 `INVALID_CURRENT_PASSWORD`, nunca 401** (401 faria o
  interceptor do PWA deslogar o usuário); nova curta → `VALIDATION_FAILED` com `errors[]`; sem auth
  → 401; todas as sessões revogadas.
- `UserService` ganhou `RefreshTokenRepository` (construtor mudou — `AuthControllerTest.setUp`
  atualizado junto).
- **Divergência:** não mexi em `FieldErrorDto`; o handler de `VALIDATION_FAILED` já cobre o caso.

### Task 5 — sort + músculos (commit `872b3be`)

- `?sort=` com whitelist (`name`, `createdAt`, `incrementKg`, `-` = desc); inválido → 400
  `VALIDATION_FAILED` via `InvalidSortException`.
- **Removido o `ORDER BY e.name` fixo** do `searchForUser` — sem isso o `Sort` do `Pageable` era
  ignorado. Nenhum nome de coluna do cliente chega ao SQL (só literais da whitelist viram `Sort`).
- `GET /api/exercises/muscles`: distintos do catálogo global + próprios, dedup insensível a caixa,
  ordenado.
- **Regra de desempate de caixa: menor valor binário vence** (`"Peito"` sobre `"peito"`). O teste
  pegou que `putIfAbsent` na ordem do banco varia com o collation — `merge` + `compareTo` é
  determinístico.
- Seed global tem 7 músculos (Abdômen, Bíceps, Costas, Ombro, Peito, Pernas, Tríceps); o IT usa isso
  como base (`$.length() == 7` prova a dedup).
